# X × Threads 話題比較・調査計画 v1.0

作成日：2026年11月6日（日本時間）  
対象：GrokBotがX、MuseがThreadsを主担当とする計画。担当は仮置きで、能力診断後に変更できる。これは実行前の計画であり、SNSの実データや調査結果ではない。

## 1. この調査で答えること

同じ日・同じ週について、次の問いを別々に扱う。

1. 両SNSで共通して注目された出来事は何か。
2. 片方のSNSで相対的に目立った出来事は何か。
3. 同じ出来事でも、評価、批判、体験談、相談、冗談などの切り口がどう違うか。
4. いつ注目が高まり、どのくらい続いたか。
5. 一つの大きな投稿、少数の発信者、多数の発信者のどれが支えていたか。
6. その差は取得方法や分類方法を変えても残るか。

比較対象は「観測条件を明示したX・Threads上の話題」である。SNS利用者全体、日本社会全体の関心、世論、到達人数へ一般化するには別の根拠が必要になる。

調査方法を開示する際は、分析単位、取得元、対象期間、取得期間、標本の作り方、件数、限界を記載する。[AAPORの開示基準](https://aapor.org/standards-and-ethics/disclosure-standards/)を、方法の記録に使う。

## 2. 中核となる手順

**独立発見 → 候補の統合 → 両SNSでの再検索 → 共通集計 → 相互監査**を基本にする。

- 最初の発見では、GrokBotとMuseに相手の候補を見せない。
- その後、XとThreadsで見つかった候補の和集合を作る。
- 表記揺れ、別名、出来事の範囲、紛らわしい語を共通の話題辞書にまとめる。
- 辞書の全候補について、双方のSNSで同じ出来事を再検索する。
- 片方にしか見つからない候補にも、同等の時間窓・語彙・探索予算を与える。
- 一部の対象を両者が再調査し、担当者による差を点検する。

「GrokBotはXしか調べず、MuseはThreadsしか調べない」設計だけでは、SNSの差と調査担当の差を分離できない。主担当を分けることと、校正のために一部を重複させることを両立させる。

## 3. 開始前に固定する条件

以下は推奨初期案。言語・地域・期間は利用目的が未指定のための仮置きで、7日間の予備調査後に確定する。

| 項目 | 推奨条件 | 理由・注意点 |
|---|---|---|
| 主担当 | GrokBot＝X、Muse＝Threads | サービスの実機能は未確認。ブランド名だけで能力を想定しない |
| 言語 | 主に日本語の公開投稿 | 日本語と日本居住を同一視しない。引用や多言語混在の判定規則も残す |
| 地域 | 公式話題面は日本設定。投稿分析は日本語圏 | 日本の地域トレンドと、投稿者の居住地は別の概念 |
| 日次 | JST 00:00以上～翌00:00未満 | UTCを併記し、境界で二重計上しない |
| 週次 | 月曜00:00以上～翌月曜00:00未満、JST | 月をまたぐ週も同じ定義 |
| 投稿の主分析 | オリジナル投稿・独自本文を伴う引用 | 返信、純粋な再投稿は別集計。形式の判別可能性を診断する |
| 内容 | テキストを基本に、画像・動画・リンク先を補助 | OCR・音声認識を使った根拠は区別し、不明な内容は推測しない |
| 観測時刻 | 原則00・04・08・12・16・20時、JST | 両SNSを同時刻帯に観測。実際の取得日時と遅延を記録 |
| 投稿の取得窓 | 各回の直前4時間 | APIごとの境界仕様に頼らず投稿時刻で最終判定。遅延分は後で再取得 |
| 反応の観測 | 可能な投稿は投稿後24時間、許容幅を事前固定 | 例えば±2時間。幅内で測れなければ欠測または別集計 |
| 更新 | 期間終了24時間後に速報、72時間後に確定 | 索引反映や分類の修正を反映。確定後の訂正も履歴化 |
| 過去データ | 取得条件を証明できる場合だけ採用 | 現在見える累計反応を過去時点の反応へ置き換えない |

正時の観測は短時間の流行を見逃す可能性がある。高精度版は1時間間隔にし、4時間版との差を評価する。片方だけ観測回数を増やした日も、主比較は両SNSで取得できた共通時刻に限定する。

前向きの継続観測を標準とする。過去の特定日・週を比較する場合は、両SNSで共通して取得できる期間と、当時のスナップショットの有無を先に確認する。当時の公式話題面の記録がなければ、現在の話題面や現在の一般検索から当時の掲載を再現したとはしない。

## 4. 公式資料から分かる取得上の違い

2026年11月6日時点で確認した公式資料を使う。実際の権限・UI・上限は開始時と変更発生時に再確認する。

| 対象 | 確認できた事実 | 設計への反映 |
|---|---|---|
| Xのトレンド | 個人化された表示と、地域を基準にした非個人化のTrending表示がある | 日本設定の非個人化された面を優先し、設定・表示面を記録する |
| Threadsの話題面 | Metaは2026年3月、日本の「話題のトピック」は利用者別の個人化ではなく、日本の利用者全体の傾向を扱うと説明している | 通常のおすすめフィードとは区別する。実際の掲載数と、表示順が順位を意味するかを確認する |
| Xの検索 | Recent Searchは直近7日、Full-Archive Searchは別のアクセス条件を持つ | 継続調査はこまめに保存する。過去期間を遡れる権限を能力診断で確認する |
| Xの反応指標 | 公開指標はリクエスト時点の値 | 投稿時刻と反応取得時刻を別々に残す |
| Threadsの検索 | Meta公式Postmanに公開投稿を探すkeyword_searchのリクエスト例がある | 検索自体の存在と、利用者が全範囲を取得できることを区別する |
| ThreadsのInsights | 投稿Insightsのリクエスト例がある | 検索で返る値、本人のInsights、第三者投稿の公開値を混同しない |

根拠：[Xのトレンド説明](https://help.x.com/en/resources/recommender-systems/trends-recommendations)、[Metaの日本向け「話題のトピック」説明](https://about.fb.com/ja/news/2026/03/threads-trends/)、[X Search Posts](https://docs.x.com/x-api/posts/search/introduction)、[X Data Dictionary](https://docs.x.com/x-api/fundamentals/data-dictionary)、[Meta公式Postman・Search for Threads Posts](https://www.postman.com/meta/threads/request/34203612-b3b2c12a-7ce6-4d86-a3c6-6d31e3b66ea1)、[Meta公式Postman・Get Post Insights](https://www.postman.com/meta/threads/request/34203612-385abc7d-b3cc-4e5d-9937-ebbe7174e041)。

Threads開発者ドキュメントの一部は確認時に取得制限があり、厳密な検索上限、過去取得窓、権限による対象範囲、日次上限はこの計画では断定しない。新着・人気の指定、期間指定、ページング、第三者指標の取得範囲を、実際の接続先で検証する。

## 5. 能力診断と測定レベル

GrokBot・Museそれぞれに、次を「可能／条件付き／不可／未検証」で報告させる。

- 接続先はSNSの検索、公式API、ブラウザ、一般Web検索のどれか。
- 日時・言語・並び順・地域を指定できるか。日時指定は実際に効いているか。
- どこまで過去へ遡れ、検索結果の上限や打ち切りを検出できるか。
- 投稿URL、ID、投稿時刻、投稿種別、投稿者識別子を取得できるか。
- 表示件数は、全数、推計、取得件数、サンプルのどれか。
- 返信・引用・再投稿・削除・非公開をどう扱うか。
- どの反応指標を、誰の投稿について、どの時点で取得できるか。
- 同じ条件を再実行した際の結果の違いと、検索ログの保存可否。
- 定時実行、前回までの状態保持、反応の再取得、ファイルへのログ保存を継続できるか。

GrokBot・Museが自律的に13週間稼働するとは仮定しない。定時実行に対応しない場合は、人または別の実行基盤が時刻ごとに呼び出し、辞書・データ・実行状態を保持する。実行主体と受け渡し先を決めるまでは、継続運用が準備できたと扱わない。

次の三つの測定を並列に扱う。どれか一つを他の代用にしない。

**A：公式話題面での露出。** 観測時刻ごとの掲載集合と掲載頻度を測る。全投稿の人気順位を測っているとは表現しない。

**B：取得範囲を説明できる投稿データ。** ページング完了まで取得した検索範囲、または抽出確率と重みを説明できる標本で、投稿・投稿者の規模を測る。あくまで定義した検索範囲であり、検索エンジンの未収録分まで全数としない。

**C：探索・内容理解のための投稿例。** 人気順上位や新着上位などから、何が語られたかを分析する。このデータでSNS全体の投稿割合や話題順位は作らない。

各話題から100件ずつ取った場合、取得件数が同じになるのは収集設計の結果である。その100件や、その中の投稿者数の大小から流行規模を順位付けしない。上限に達した件数は「少なくとも取得した件数」として残す。

候補の一部が打ち切られている場合も、残りだけで完全な上位順位を確定しない。打ち切り候補が上位に入る可能性を検討し、下限表示、部分順位、順位保留を使う。ページングの終了だけで、仕様上の隠れた上限まで否定できるわけではない。

両SNSでBを同じ水準で実行できなければ、主な比較をAとCにし、数量比較の範囲を明確に狭める。Xだけで取得できる全数や指標はXの補足に置く。

## 6. 話題を発見する方法

単一の検索面に依存せず、以下を経路別に記録する。

1. 日本設定の公式トレンド／話題面。
2. 利用可能な新着・人気・キーワード・トピック検索。
3. 予備調査で選び、その後固定する分野別の観測対象。生活、仕事、子育て、健康、食、娯楽、スポーツ、政治、経済、技術などを含める。
4. 独立したニュース・発表・イベントカレンダー。出来事の日時確認と検索漏れの検査に使い、SNS人気の証明には使わない。
5. トレンド掲載のない候補を探すための探索枠。例として発見予算の3分の1を確保する。

分野別の探索枠は見落としを減らすために使い、最終ランキングに各分野の枠を強制しない。分野別アカウントの観測は固定パネルとして明記し、SNS利用者全体の代表標本とは呼ばない。

初期案は各SNSが1日あたり20～30件の候補を提出する。これは探索予算の上限案であり、話題が存在しない日に埋め合わせない。最終表示は上位10件と、片方で目立った5件程度を目安にし、収集を最初から上位10件だけに限定しない。

検索負担は「候補数 × 語彙群 × 時間窓 × ページ数」で増える。予備調査で実測し、同じ候補について双方に同等の探索機会を与えられる範囲まで絞る。弱い話題だけ片方で追加検索するような運用は避ける。

受け渡しの初期案は、各観測枠の終了後30分以内に独立候補を提出、1時間以内に統合担当が共通辞書を返却、3時間以内に両者が一次再検索を提出すること。実行能力と費用に合わせて予備調査で確定する。日中は辞書を更新し、日次の候補一覧はその累積から作る。遅く見つかった投稿で24時間後の計測を逃した場合は、成熟時間をそろえた反応比較から外す。

本番で予算上限が迫ったら、統合担当へ未処理範囲を返し、共通候補・時間窓を双方で対称的に縮小する。未処理はNOT_COLLECTED、途中の打ち切りはCAPPEDとし、結果がある話題だけで全体順位を確定しない。

## 7. 話題辞書と同一話題の判定

話題を「大分類 → 出来事 → 切り口」の三層で管理する。

例：経済 → 企業Aの特定四半期決算発表 → 好業績への評価／株価への不満／従業員の体験談。

- 比較の主単位は出来事。同じ人名でも別の事件は分ける。
- 正式名、略称、ハッシュタグ、俗称、誤記、関連リンクを記録する。
- 除外語、同名別人、古い出来事の再拡散を指定する。
- 広い生活テーマは、安易に一つの事件と同じ粒度で順位付けしない。分野別の継続テーマ表を別に作る。
- 複数の出来事を含む投稿は、主集計では中心となる一つを付与し、二次ラベルを保持する。曖昧な投稿は保留にする。
- 主題が定まらない投稿を無理に配分しない。複数ラベルの分析では、割合の合計が100％を超え得ることを明示する。
- 辞書の統合・分割・語彙の追加には版を付ける。追加語が検索範囲を変える場合は比較期間と基準期間を再取得するか、系列を区切る。

分類は可能ならSNS名や反応数を隠した共通投稿セットで校正する。プラットフォームが予想する語り方へ分類を引っ張らない。

## 8. 注目度と比較指標

一つの総合点に押し込まず、次の軸を併記する。

| 軸 | 指標 | 計算条件 |
|---|---|---|
| 投稿規模 | 重複除去後の関連投稿数 | Bで、取得範囲と打ち切りが分かる場合 |
| 発信の広がり | SNS内で重複除去した投稿者数 | 投稿者識別子が取得でき、話題間の取得条件が比較可能な場合 |
| 偏り | 上位1％の発信者の投稿割合、投稿者集中度 | 標本設計と件数が支える範囲で算出 |
| 急増 | 同じSNSの通常時に対する増加 | 同じ取得条件の基準期間がある場合 |
| 持続 | 掲載観測率、活動時間帯数、注目日数 | 観測回数と欠測を併記する |
| 反応 | 投稿後24時間のいいね・返信・引用・再共有など | 同じ定義・同じ経過時間で取れる指標のみ。別々の列で扱う |
| 公式露出 | 共通の有効観測回に占める掲載回数 | Aの掲載指標。投稿総数の代用にしない |
| 語られ方 | 評価、批判、相談、体験談、情報共有、冗談など | Cを含む。標本範囲を明記し、態度と感情を分ける |

### 算式と分母

- 公式掲載観測率の主比較 ＝ 両SNSで取得に成功した共通観測枠のうち、そのSNSで掲載が確認できた回数 ÷ 両SNSで取得に成功した共通観測枠数。予定枠が同じでも実際の取得時刻が離れすぎた回は除く。許容差は予備調査で固定する。
- 各SNSの全成功回を分母にした掲載観測率も補足で出し、主比較の対象回数と対象外の回数を示す。
- 構成比 ＝ 関連投稿数 ÷ 事前定義した同一観測集合の投稿数。検索上位100件の割合を、SNS全投稿の割合としない。
- 投稿者構成比を出す場合も、分母は同一条件で観測した投稿者集合に限定する。SNS間の同一人物推定は行わない。
- 急増倍率は、同じSNS・同じ時間帯・同じ曜日の過去4週程度を参照して算出する。分母が取得できる場合は、観測対象全体の活動量の増減も補正する。
- 基準値がゼロや欠測の場合、無限大の急上昇順位を作らず「新規観測」「基準不足」と表示する。
- 基準となる4週は十分な精度を保証する期間ではない。ばらつきや外れ値の影響も併記する。

### SNS間で比べる値

1. それぞれのSNS内での、取得範囲を明示した順位。
2. 同じSNSにおける平常時からの増加。
3. 共通候補のうち上位に入った出来事の重なり。
4. 各出来事の切り口、観測上のピーク、継続性。

生のいいね、閲覧数、投稿数だけで「Xの方が関心が強い」と結論しない。順位や百分位に変換しても、検索の選択バイアスが消えるわけではない。

公式話題面の表示順が順位を表すと確認できない場合、表示順を数値順位として分析しない。両SNSの掲載数が違う場合は掲載件数も表示する。共通の深さで切りそろえる追加分析は、双方の順序が順位として確認できる場合だけ行う。

総合順位が必要になった場合は、採用指標、重み、欠測の扱いを先に固定し、重みを変えたときに順位が逆転する話題を明示する。今回の標準案では、規模・急増・公式露出を別表にする。

## 9. 日次・週次・時差の集計

**日次**では、投稿が作成された日の出来事と、その日に増えた反応を混ぜない。

- 標準：その日に作成された投稿を集計する。
- 補足：前から存在する投稿への、その日中の反応増加を追う場合は別の表にする。
- 累計値の差分には、削除や計測変更による減少もあり得る。負の差分を黙ってゼロにせず理由を検査する。
- 数日前の投稿の再拡散も、発生日と再注目日を区別する。

**週次**は日次順位の平均や、日次投稿者数の単純合計から作らず、元データから再計算する。

- 週内の投稿ID・投稿者を重複除去する。
- 週全体の規模、最大の日次規模、ピーク日、注目が続いた日数を出す。
- 1日だけ急増した話題と、毎日安定して続いた話題を並べて示す。
- 途中から観測した週は未完の週とし、完全な週と同列に順位比較しない。

**話題の一致**は、まず共通上位K件の重なりを示す。K＝10・20など複数条件で確認する。集合のJaccard係数は「共通の出来事数 ÷ 両SNSの出来事の和集合数」。双方の集合が空なら欠測とする。これは候補集合に依存する記述値であり、全話題の一致率ではない。

**先行・遅行**は、比較可能な時間窓と十分な観測がある出来事だけを対象とする。最初に基準を超えた観測区間とピーク区間を比較し、4時間間隔なら時刻精度もその程度に限定する。Xが先に観測されても、XからThreadsへの伝播や因果関係が証明されたとはしない。

## 10. 誤差・重複・偏りを検査する

- 同じ投稿IDの重複は除去。転載、定型文、リンクのみ、キャンペーン参加、純粋な再投稿は別フラグにする。
- 別SNSへの同じ本文の投稿は、SNS別の活動として残し、必要なら横断転載の補足分析を行う。
- 自動投稿や協調行動は、観測可能な特徴として記録する。AIの印象だけで特定の投稿者をボットと断定しない。
- 広告・PR・懸賞は判別できるものを表示し、含む集計と影響を抑えた集計を比べる。見えない広告効果を完全に除去したとはしない。
- 大口投稿者、一件の巨大投稿、特定コミュニティへの集中を検査する。
- 日本語以外、画像・動画中心、削除済み、非公開、検索非掲載などの見落としを記録する。
- 返信は元投稿よりアクセス条件が異なる可能性があるため、共通条件で取れる範囲を別分析する。
- 利用規約とアクセス条件に沿って取得し、認証情報は収集ログへ入れない。公開URL・ID・必要な観測値を中心に保存し、個人情報や本文の保持を必要最小限にする。

過去のTwitter研究でも、標本と広い取得範囲では話題等の分析結果がずれ得ることが検討されている。現行API仕様の根拠ではなく、取得経路を監査する理由として参照する。[Morstatter et al., 2013](https://arxiv.org/abs/1306.5204)。

## 11. 校正・相互監査・品質ゲート

### 校正

予備調査の1日について、可能なら両者がXとThreadsの両方を調査する。難しければ共通の公開投稿セットを両者に分類させる。後者で揃うのは分類・集計であり、検索能力の差は残る。

本調査では、話題候補・時間帯を層別して無作為に選び、初期案として10～20％を相互監査する。主担当は担当SNSの全対象を処理し、監査対象だけもう一方も処理する。

相互監査で比べるのは、発見候補、検索範囲、投稿時刻、重複処理、出来事ラベル、切り口、証拠との一致。分類は単純一致率と不一致の内訳を示す。必要に応じ偶然一致を考慮する指標も使うが、数値だけで妥当性を保証しない。

### 品質ゲート

| ゲート | 確認すること | 未達の場合 |
|---|---|---|
| 範囲 | 期間・言語・検索面・投稿形式が固定されている | 固定して再取得／対象を限定 |
| 取得 | 有効な観測回数、上限、エラー、ページング終了が分かる | 欠測・打ち切りを表示、規模順位を保留 |
| 証拠 | 掲載根拠と投稿根拠を照合できる | 主張を弱めるか対象から保留 |
| 比較 | 同じ意味の指標・期間である | 共通指標だけで比較 |
| 分類 | 辞書と判断基準が一致している | 辞書改訂と該当部分の再分類 |
| 再現 | 入力・取得日時・方法・版を追跡できる | 再現不能な数値を確定結果にしない |

運用上の初期目標は、各SNSの予定観測回の90％以上を取得し、SNS間の取得成功率の差を5ポイント以内にすること。ただし、この数字は研究の妥当性を保証する基準ではなく、予備調査で調整する運用値である。

話題の説明には、可能なら異なる投稿者の公開投稿を3件以上用意する。これは内容を確認する最低限の例であり、流行規模の証明ではない。公式話題面に掲載されたが投稿が取れない場合は、その二つを分けて報告する。

信頼度は根拠の種類、観測の充足度、辞書の安定性として説明し、AIに「信頼度95％」のような根拠のない確率を生成させない。非確率的な検索上位のデータに狭い信頼区間を付けても、検索外の偏りは評価できない。

## 12. 結論を出す前の感度分析

重要な結論は、次の条件を変えて再計算する。

1. 上位K件のKを10・20などに変える。
2. 純粋な再投稿・返信を含める／分ける。
3. 定型文・懸賞・疑わしい高頻度投稿者の影響を抑える。
4. 上位投稿者や一件の巨大投稿への依存を弱める。
5. 取得経路を公式話題面・新着検索・人気検索などで分ける。
6. 話題の統合粒度を出来事単位・継続テーマ単位で比較する。
7. 両SNSで取得に成功した共通時間帯だけを使う。
8. 日付境界付近の話題を検査し、必要なら別の境界で補足分析する。

「片方だけで盛り上がった」「先に広まった」という結論は特に厳しく検査する。追加検索を行っても検出されなかった場合は「今回の条件では未検出」と書く。検索不可と不人気を同一視しない。

結果の言い方は「条件を変えても差が残る」「条件によって変わる」「僅差」「判定不能」を使い分ける。

## 13. 保存するデータと欠測コード

実施時は、CSVまたはJSONL等の機械可読データと、読者向けの報告を分けて残す。以下はテーブル設計であり、この計画作成では実データを収集していない。

| テーブル | 主な項目 |
|---|---|
| 観測ログ | run_id、protocol_version、担当、SNS、検索面、クエリ、並び順、地域・言語設定、対象開始・終了、取得日時、上限、取得状態、件数、費用 |
| 投稿 | SNS＋post_id、URL、SNS内投稿者識別子、投稿日時、取得日時、投稿種別、話題ID、反応の値と観測日時、重複・PR等のフラグ |
| 話題辞書 | topic_id、大分類、出来事、切り口、別名、検索語、除外語、統合・分割理由、辞書版 |
| 集計 | SNS、期間、topic_id、測定レベル、観測範囲、分子・分母、順位、急増、持続、欠測理由、品質情報 |
| 監査・訂正 | 監査対象、双方の判断、食い違い、確認根拠、解決方法、再集計の版 |

欠測やゼロを、次のように区別する。

- 0：定義した取得範囲を調べ、実際に該当件数がゼロだった。SNS全体のゼロは意味しない。
- NOT_DETECTED：検索を実施したが、その条件では検出されなかった。
- NOT_COLLECTED：調査していない。
- UNAVAILABLE：権限・機能・エラー等で取得できない。
- CAPPED：検索・取得上限に達し、全数は分からない。
- BASELINE_MISSING：平常時の比較基準がない。
- REMOVED：取得後に削除・非公開となり、再確認できない。

一般読者向けには日本語で理由を書く。投稿者識別子は分析上必要な範囲で管理し、公開報告に不要な識別情報を出さない。本文・画像・認証情報の無制限な複製保存を前提にしない。

## 14. 毎日の報告と週の報告

日次の表は、次の項目を並べる。順位が作れない条件では、その列を欠測として理由を付ける。

| 日付 | 出来事・共通ID | X内順位／掲載 | Threads内順位／掲載 | 平常時比 | 投稿者の広がり | 主要な切り口の違い | 根拠 | 取得・品質 |
|---|---|---|---|---|---|---|---|---|
| 対象日 | 実データから記入 | 対象範囲を併記 | 対象範囲を併記 | 基準がある場合 | 比較可能な場合 | 投稿例で裏付け | 公開URL等 | 欠測・上限等 |

日次の読者向け記述は「共通して目立った出来事」「Xで相対的に目立った出来事」「Threadsで相対的に目立った出来事」「同じ出来事の切り口の差」「判定に限界がある箇所」の順にする。件数を固定して無理に埋めない。

週次はこれに、週の上位話題の重なり、日ごとの推移、急増と持続の区別、ジャンル構成、観測上の先行・遅行、品質の変化を加える。

図を作るなら、話題×日付のヒートマップ、SNS別順位の対照、共通話題・片側で目立った話題の集合図が有用。各図には対象範囲を表示し、欠測をゼロと同じ色にしない。

## 15. 進め方と予算

推奨フル版は合計13週間。開始日は指定しない。

| 段階 | 期間 | 完了条件 |
|---|---|---|
| 予備調査 | 7日 | 能力診断、同一課題の校正、探索費用測定、辞書・指標・停止規則の確定 |
| 基準期間 | 28日 | 両SNSで同じ方法の基準データを確保。この期間も日次・週次の記述比較は可能 |
| 本調査 | 56日 | 日次・週次報告、相互監査、感度分析、最終比較 |

基準期間を含む過去データが両SNSで同じ条件で取得できる場合は、前向きに28日待つ必要はない。現在の検索で得た過去投稿の反応数は、当時の反応スナップショットと同一扱いしない。

短縮版は予備7日＋本調査28日。基準不足の間は急増指標を出さず、公式掲載、観測できた話題、語られ方の比較から始める。長期傾向の主張は限定する。

費用は、投稿取得・検索・反応再取得・画像音声の理解・分類・監査・保存に分けて測る。利用サービス未確定のため金額は断定しない。日次の検索回数、ページ数、候補数、総費用に上限を設ける。

予算超過時の削減順は、補足的な画像音声分析や高度な時差解析 → 探索する候補の深さ → 観測間隔。主たる比較範囲、両SNSの対称性、根拠・欠測ログは維持する。どの削減でも方法版と解釈範囲を更新する。

## 16. 採用する最終方針

GrokBot＝X、Muse＝Threadsを主担当とし、共通の話題辞書・時間窓・出力形式を使う。独立に発見した候補を統合してから双方で調べ直す。公式の話題面、取得範囲内の規模、平常時からの急増、語られ方を別々に集計する。日次と週次は元データから作り、担当者の差と取得の偏りを監査する。

この条件で、二つのSNSの「同じ出来事への注目の違い」と「それぞれで独自に目立った話題」の両方を、根拠と限界付きで比較できる。
